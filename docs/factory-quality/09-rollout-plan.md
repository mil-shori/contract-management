## 週1〜3：収録PoC ← **ここを飛ばさない**

**コードを1行も書かずに実施する。** 手動で全工程を通し、実用性を判定する。

### 手順

1. iPad で 1〜3分の動画を **10本**録る（#01 の巡回テンプレート＝付録C に沿って）
   - うち2本は**騒音の大きい工程**で録る ← これが判定の本命
   - うち1本は設備メンテの観点で録る
2. Google Cloud Console から Speech-to-Text v2 (`chirp_2`) に手動でかける
3. 文字起こし＋フレーム3枚を、付録Bのプロンプトで Claude にかける
4. 出てきたカードを**本人が読む**

### 判定基準

| 項目 | 合格ライン | 割った場合 |
|---|---|---|
| **騒音下の文字起こし** | 判断基準の数値・固有名詞が正しく拾えている | ピンマイク導入 → 再測定。それでもダメなら撮影と口述を分ける |
| **カードの内容** | 本人が「これは自分の観点だ」と言える | 収録の型（質問の順番）とプロンプトを直して2に戻る |
| **`why` の充足** | 10本中、半分以上のカードに `why` が入る | 定型質問に「なぜそうするのか」を明示的に足す |
| **1本あたりの所要時間** | 撮影1〜3分＋承認1分以内 | 収録の型を短くする |

**ここで分かれば、プロンプトと収録の型を直すだけで済む。実装後に分かると作り直しになる。**

## KPI 測定方法

| 指標 | 取り方 | 頻度 |
|---|---|---|
| 社内不良率 | 既存の品質記録から | 月次 |
| 逸脱件数（記録の空欄・後埋め） | 巡回時に数える | 週次 |
| 点呼提出率 | `workReports` / 対象作業回数 | 週次 |
| フラグ率 | `flagged=true` / 全 `workReports` | 週次 |
| 承認済みカード数 | `cards` の `status=approved` | 週次 |
| ボット利用回数 | `botSessions` のターン数 | 週次 |
| **未整備で返した質問数** | `knowledgeGaps` の `status=open` | 週次 |
| **新人が単独作業に到達する日数** | 認定制（#01 §4）の記録から | 都度 |

### 週次レビュー（30分・固定枠）

1. 詰まった箇所ランキング上位5工程（#01 §7）
2. 未整備の質問（`askedCount` 順）→ 次に録るテーマを決める
3. 未承認カードの残数 → 溜まっていたら収録を止める
4. **人を責める会議にしない**

---

## リスクと対処

| リスク | 影響 | 対処 |
|---|---|---|
| **騒音下のSTT精度が出ない** | 仕組み全体が成立しない | 週1〜3のPoCで判定。ピンマイク or 撮影と口述の分離 |
| **承認が溜まる** | データが腐り、ボットが古くなる | 週1回30分の固定枠。溜まったら収録を止める |
| **現場が監視と受け取る** | 使われなくなる | #08 の線引きを**導入前に**説明。記録を本人に開示 |
| **動画容量でコストが膨らむ** | 継続できない | 1本1〜3分・720p のルール＋ライフサイクルルール |
| **カードの質が低い** | 誤った内容が現場に出る | 承認を飛ばさない（#05 の大原則） |
| **社長の時間が取れない** | 全部止まる | 収録は1日10分・週2回から。増やさない |

**最後のリスクが実は一番大きい。** 収録も承認も社長本人にしかできない作業なので、
**週あたり1時間で回る設計**を維持する。回らなくなったら、対象工程を減らす。

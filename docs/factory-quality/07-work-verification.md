# チケット #07: Phase 2 — 動画点呼による遵守確認

## 現場の流れ

工程ごとに、作業者が iPad で次を行う。

```
① 手順動画（30秒・母語音声）を見る
② 自分の作業を録りながら、やったことを口で言う（30〜60秒）
③ 送信
```

Phase 1 で作った「録って話す」パイプライン（#04）が**そのまま使える。**
違いは `capture.role = work_report` と、出口が突合処理になることだけ。

---

## 1. 作業者は母語で話してよい

**ここが外国人労働者対応の核心。**

日本語での申告を求めると、この仕組みは即座に形骸化する。
言えないから黙る、黙るから記録が残らない、記録が無いから改善もできない。

- STT の `language_codes` に母語を含める（自動判定）
- 突合は翻訳を経由して行う
- フィードバックも母語で返す

---

## 2. 突合ロジック

チェックリスト（`checklists/{processId}`）の各項目について、
**文字起こし＋フレームから3つのいずれかに分類**する。

| verdict | 意味 |
|---|---|
| `mentioned` | 実施したと言及があり、映像とも矛盾しない |
| `not_mentioned` | 言及が無い（やっていないとは限らない） |
| `contradicted` | 言及または映像が手順と矛盾する |

各判定に**根拠となる発言の引用とタイムコードを必ず付ける**（#04 と同じ原則）。
根拠を出せない判定は出力させない。

```python
# 判定は1リクエストでチェックリスト全項目をまとめて処理する
# output_config.format で results 配列のスキーマを強制
```

## 3. レビュー運用：全件は見ない

**全件レビューは不可能。** 人員が増えるほど、そこが新しいボトルネックになる。

| 対象 | 扱い |
|---|---|
| `not_mentioned` / `contradicted` を含むもの | **管理者キューへ**（`flagged: true`） |
| それ以外 | 記録のみ。レビューしない |
| 全体からランダム5% | 抽出レビュー（フラグの精度を測るため） |

**ランダム抽出を必ず入れる。** これが無いと、AIの見落とし率が分からないまま
「フラグが少ない＝守られている」と誤読する。

---

## 4. フィードバックは、その日のうちに、母語で

- 翌週の朝礼では遅い。作業の記憶が残っているうちに返す
- 「できていなかった」ではなく「ここを確認させてください」の形で聞く
- 返すのは**同じ母語のリーダー経由**が望ましい（#01 §5）

---

## 5. 制度面の線引き（必ず規程に書く）

| 決めごと | 内容 |
|---|---|
| **フラグは違反認定ではない** | AIの判定は「疑い」。懲戒の一次証拠にしない |
| **撮影の目的を明示する** | 品質改善と教育のため。人事評価には使わない |
| **保存期間を明示する** | #08 と一致させる |
| **閲覧できる人を明示する** | `manager` 以上と本人のみ |
| **本人が自分の記録を見られる** | 監視ではなく鏡（#01 §8） |
| **同意を書面で取る** | 母語版を用意する。詳細は #08 |

**この線引きを最初に全員に説明する。** 後から説明すると、監視されていたという受け取り方になる。

---

## 6. 段階的な導入

いきなり全工程に入れない。

| 段階 | 範囲 | 目的 |
|---|---|---|
| 1 | **1工程・協力的な数名** | 突合の精度を測る。UIの詰まりを見つける |
| 2 | 1工程・全員 | 運用が回るか。レビュー負荷はどれくらいか |
| 3 | 重要工程3つ | 横展開の型を作る |
| 4 | 順次拡大 | — |

段階1で**突合の誤判定率が高すぎる場合は、そこで止める。**
誤判定が多いフラグは、現場の信頼を壊してから精度が上がっても手遅れになる。

---

## 7. 期待される副産物

点呼の記録は、遵守確認以外にも効く。

- **フラグが集中する工程＝手順の欠陥**（#01 §7 の入力になる）
- 新人が何につまずくかが見える → 教育内容の改善
- 「言えない」項目が見つかる → 手順の言語化が不十分な箇所
- 優良な作業の記録が、そのまま**次の手順動画の素材**になる

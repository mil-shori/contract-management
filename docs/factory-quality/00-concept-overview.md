# チケット #00: 全体構想 — 食品工場 品質担保システム

## 背景と課題

工場拡大に伴い人員が増えたことで、品質担保が崩れつつある。

- 写真・マニュアル・タブレットは整備済みだが、**見ながら作業する仕組みだけでは守られない**（特に外国人労働者）
- 経営者本人が持つ「現場を見る観点」「設備メンテの観点」が**暗黙知のまま個人に閉じている**
- 人が増えるほど、その観点は希薄化し、伝言ゲームで劣化する

## この構想が解こうとしていること

| # | 課題 | 打ち手 |
|---|---|---|
| 1 | 経営者の観点が形式知になっていない | 巡回を**動画＋音声で録り、構造化してナレッジ化** |
| 2 | 困ったときに聞ける相手が経営者しかいない | ナレッジを**iPadから開ける社内ボット**にする |
| 3 | マニュアルが守られたか分からない | 作業者が**動画を回しながら口頭で作業を申告**する |

## 設計の中心：「録って話す」を1つの共通部品にする

社長の巡回記録と、作業者の遵守確認は、**まったく同じ操作**で成立する。
ここを1つの共通部品にすることが、この設計の核。

```
録る（動画 or 音声）＋ 話す
        ↓
   文字起こし（多言語自動判定）
        ↓
   フレーム抽出（数秒間隔）
        ↓
   LLMで構造化 → カード1枚（出典タイムコード付き）
        ↓
   人が承認（1枚ずつ、スワイプ）      ← ここを飛ばさない
        ↓
   ├─ ナレッジ／マニュアル（社長の観点）
   └─ 遵守チェック結果（作業者の申告）
```

同じパイプラインを、入力の役割（`capture.role = patrol | maintenance | work_report`）で
出口だけ振り分ける。**Phase 1 で作ったものが、Phase 2 でそのまま再利用される。**

## 段階計画

| Phase | 期間目安 | 内容 | チケット |
|---|---|---|---|
| **0** | 週0〜3 | 決めごと＋**コードを書かない収録PoC** | #09 |
| **1** | 週3〜8 | 収録 → 文字起こし → 構造化 → 承認 → iPadボット | #02〜#06 |
| **2** | 週8〜12 | 動画点呼による遵守確認を1工程で試験 → 横展開 | #07 |
| **並行** | 全期間 | 現場運用設計（守らせる仕組み・非システム施策） | #01 |

**Phase 0 を飛ばさない。** コードを書く前に10本録って、カードの質が実用水準に届くかを確かめる。
ここで分かれば、プロンプトと収録の型を直すだけで済む。実装後に分かると作り直しになる。

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 実装場所 | **別リポジトリで新規構築** | 契約管理システムとデータ・権限を完全分離する |
| 優先スコープ | **ナレッジ収集とボットが先** | 暗黙知の形式化が拡大局面で最も効く |
| 遵守の担保方式 | **動画を回しながら口頭で話す** | 静止画のAI OK/NG判定は教師データ収集コストが高く、固定カメラ常時監視は労務ハードルが高い |
| 対応言語 | **設定ファイル駆動で後から追加** | 現時点で主要母語が未確定のため、ハードコードしない |

## KPI

| 区分 | 指標 |
|---|---|
| 品質 | 社内不良率、クレーム件数、逸脱（記録の空欄・後埋め）件数 |
| 遵守 | 点呼提出率、フラグ率（下がるべき）、再教育後の再発率 |
| ナレッジ | 承認済みカード数、ボット利用回数、**「未整備」で返した質問数**（＝次の収録テーマ） |
| 教育 | **新人が単独作業に到達するまでの日数** ← 拡大局面で最も効く指標 |

## コスト感（月額レンジ）

| 項目 | 目安 |
|---|---|
| Firebase / GCP（Storage・Functions・Firestore） | 数千〜2万円 |
| Speech-to-Text | 録画の総分数に比例 |
| Claude API（カード起案＋ボット） | 利用回数に比例 |
| **合計** | **月3〜8万円程度のレンジ**（動画量次第） |

最大の変動要因は録画の総分数。**「1本1〜3分」の運用ルール**がコスト管理も兼ねる。
